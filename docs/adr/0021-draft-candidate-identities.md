# M6.2 候选身份与真实所属模块

本记录只解释 `PRODUCT_DESIGN.md` 3.0.7 §20.1、§20.8、§20.9 的内部实现，不增加产品规范。

现有 Import 草稿保存在 `drafts`，单块和组生成候选分别由 Authoring 的不可变记录保存。旧 `reviews` 外键只指向 Import 表。直接把生成候选写成带假 `import_id` 的 Import 草稿会丢失真实来源；通过 ID 前缀或轮询多张表猜归属也无法作为权限判断。

0016 增加稳定身份表与不可变候选修订表。身份保留真实 workspace、owner、具体来源种类和 entity；审核外键绑定这些字段以及确切 draft revision 和 candidate SHA。旧审核原字段保留，不能用审核回执里的声明重建已经缺失的候选。无法匹配原候选时，迁移整体回滚并保留 Database 已建立的迁移前备份。SQL 的字段/关系检查不代表重新计算了原始字节的 SHA，更不代表批准内容。

`DraftCandidates.admit` 是调用方事务内的内部端口。调用者明确指定来源种类，实际 owner 重新核验原始材料与完整历史；Authoring 使用同一连接的 `verify_history` 检查源 Job、Context 和 CheckedProvider 产物。当前作者会话与 Policy 每次重核，包括已有登记的重试。只有这些检查成功才登记身份；重试不替换记录，源损坏不通过已有登记放行。该端口不开放 HTTP，不创建审核或发布内容。

Import 的 candidate SHA 沿用原公开元数据定义，不能据此批准其预览中的私有答案。生成组的 SHA 则保留原完整组（含私解）的绑定。两种来源不被强行解释成相同的批准范围。原 `/drafts/{id}`、Authoring 单块/组读口及其固定 `state=draft` 形状保持原义。

后续 M6.2 仍需在规范中具体化编辑草稿读写、审核适用性、证据附件绑定、数值检查发布门槛、组发布映射、差异/影响与恢复命令，再接入实际 HTTP 和 UI。此基础切片的测试不替代人工数学/来源审校、发布验收或教学效果验证。
