# 0035: Freeze Content impact evidence in the publication transaction

Status: implemented as a narrow M6.2 Content-owner slice; impact reconciliation and M6.2 acceptance remain open.

`content.dependencies_invalidated` already carries exact old/new `ContentRef`s and a conservative `affected_ids` closure. Those IDs include historical dependency edges and do not, by themselves, establish which revision of a dependent uses the changed revision. A read-side reconstruction from current `object_dependencies` is unstable: a concept-ID edge can change `target_revision` after publication, and events with equal `created_at` microseconds cannot be ordered by the clock. The first read-only impact implementation at `00dbe4f` also used deferred `BEGIN`, allowing an independent attempt to start between the Policy check and the read.

Migration `0021_impact_event_snapshots.sql` adds an insert-only Content-owned event snapshot. Publication writes it in the same transaction as the new revision, current pointer, paired `content.published` and `content.dependencies_invalidated` outbox events. The snapshot binds the event ID, workspace, original outbox payload SHA-256, exact old/new refs, conservative affected IDs and a revision-qualified list of **explicit** dependent `ContentRef`s. The producer traverses `reference` and `anchor` rows only when each target ref appears in the immutable owner revision metadata. Pure concept-ID relations cannot prove a revision-qualified target; their owners remain conservative candidates even if a mutable edge row contains `target_revision`. Failed evidence insertion rolls back publication.

`owner_frozen_v1` means this transaction froze the explicit-ref closure found through those validated rows. The impact read checks the original event and paired published event, workspace, payload and snapshot hashes, old/new revision identity, and the frozen refs against immutable owner metadata. An event whose cited revision is missing fails as corrupt evidence, not as an absent event. The read intentionally does **not** rescan current `object_dependencies`. A later bypass mutation to a current explicit-ref or concept edge therefore cannot rewrite a historical answer and will not be reported as a current-edge integrity diagnosis. This evidence does not prove the present dependency graph is complete or untampered. `affected_ids` remains a conservative event-time candidate list; `exact_dependency_refs` must not be extended from a bare concept ID or a sibling block. Every returned applicability remains `pending_review`, with no downstream completion claim.

The initial review expected a modified current explicit edge or a cross-workspace concept edge to make the read fail closed. That expectation applied to the old live-edge reconstruction, not to the frozen historical projection. The corresponding tests now assert stability of the original frozen result and explicitly explain this changed boundary. The original review's RED repros are preserved by the concept-revision tamper, equal-microsecond publication and concurrent attempt tests; they turn GREEN with transaction-frozen evidence and `BEGIN IMMEDIATE` before `PRAGMA query_only=ON`. The query-only connection is rolled back after the read, and the tests verify a concurrent writer cannot cross the Policy check and no DML persists.

Migration time registers existing invalidation event IDs and their original payload bytes as `legacy_unverified`. Those events get no inferred exact refs and are not retroactively promoted. A post-migration event whose frozen row disappears cannot masquerade as legacy: its ID is absent from that immutable registration and readback fails `CONTENT_HASH_MISMATCH`. This distinction relies on the applied migration and SQLite storage integrity; the self-hash and triggers do not constitute an external, malicious-database attestation. If a database was already corrupted before migration, this slice cannot reconstruct trustworthy historical exact edges.

The read is an internal `ContentService` query. PRODUCT_DESIGN.md Appendix A has no impact HTTP route, so none is inferred. Notes' existing stale handling, recommendation dirtiness, retrieval invalidation, question and grade history, human review decisions, and restoration by higher reviewed revision remain with their existing owners and workflows. This slice does not mark any of them reconciled.
