# 0023 — Quality review history storage

M6.2 engineering decision under PRODUCT_DESIGN.md 3.0.7, sections 7, 15, 20.1, 20.3, 20.4, 20.6 and Appendices A–C. This is a forward storage slice, not review or publication acceptance.

Migration 0017 adds four empty Quality-owned tables. It does not change 0001, 0016, core contracts, or existing receipt bytes, and never backfills a Job, machine report or human approval from a legacy review. The migration runner's existing transaction and online backup protect both schema and data on failure. Legacy reviews retain their original claims; new checked application reads must distinguish them from authenticated new history.

`review_jobs.review_id` is the actual `draft_review` Job ID. Composite foreign keys bind its workspace and kind, complete catalog candidate revision, and immutable catalog source kind. The extra source-kind unique index is necessary because 0016's revision key alone does not distinguish Authoring single and group producers. Additional parent unique indexes are redundant with their primary keys and do not rewrite parent rows. Jobs ports remain the only production writers of Jobs/events; migration tests use explicitly synthetic SQL fixtures.

`review_revisions` starts with machine revision 1. Later rows are human-decision records with a generated immediate predecessor number and a foreign key to that same review's predecessor receipt hash. History insertion also requires the current `reviews` projection to name the exact candidate registered for that Job. `reviews` remains mutable: the future Quality transaction must CAS its current revision and atomically append the complete record/artifact/command history, and every protected read must check the complete chain against the current projection. These SQL constraints alone do not establish those application transactions or authenticate human verdicts.

`review_artifact_bindings` preserves original attachment order and binds an actual artifact's ID, workspace and blob hash to an actual review revision. Its owner label is a closed dispatch tag, not an authenticated ownership claim. Future Import/Quality ports must check the real profile, manifest, bytes, current permissions and original owner history. Numeric ledgers remain with their existing owners; they are not cast into Import artifacts. All four new tables reject UPDATE, DELETE and REPLACE during normal operation. The artifact guard covers both ordinal and artifact-ID uniqueness even with SQLite recursive triggers disabled.

`review_commands` retains the exact workspace/actor/route/key and original request/ACK JSON and hashes. Its command kind separates revision domains: create binds the candidate basis and initial Job revision, decision binds adjacent retained Review revisions, and cancel binds actual Jobs event sequence numbers for its basis/result. Generated domain columns and composite foreign keys keep those revision references valid after insertion, including against later event deletion/rekeying. Object-specific routes include their original IDs. Creation requires no nonexistent ReviewReceipt; cancellation before a machine report also remains representable. These relational checks do not validate ACK shape, request equality, canonical JSON/hash authenticity, event semantics or current actor permission. Checked owner/Jobs ports must do that before replay. A same-key operation is never overwritten with a new ACK.

Historical actor IDs are opaque identities, not session tokens and not foreign keys conferring current access. `reviews.reviewer_session_id=NULL` remains legal, including the existing backup script's isolated-copy cleanup; original receipt and immutable history bytes stay unchanged. Removing replay-only command material during full export requires a separately reviewed owner backup port and explicit manifest exclusions. This migration does not claim M7 export/restore completeness. Append-only guards protect normal operations and do not remove the documented future maintenance/purge workflow.

SQLite JSON validity, integer/hash shape and foreign keys are not proof of current Policy, owner authenticity, actual machine work, mathematical/source approval or hash integrity. Those checks belong to the subsequent Quality repository/worker/HTTP slice. No worker, HTTP route, provider call, numeric execution, generated ReviewReceipt, or publication path is introduced here.
