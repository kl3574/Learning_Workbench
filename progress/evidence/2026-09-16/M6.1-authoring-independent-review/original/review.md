# Independent Authoring generation review — four actual counterexamples

Scope: PRODUCT_DESIGN 3.0.6 SHA `30220c34fe7312887f5bcb1c67406c9638f1719ff3ed7bc9e95d7d5085b5d924`; root-owned Authoring service/context/source/worker/repositories and main/HTTP/Jobs/security/Consent diffs. B's numeric repository/service and C's UI are excluded. Numeric worker registration was explicitly not implemented at review start and is not reported as a new finding. No repository file was modified by this review. No browser/vendor/credential call was made; the four probes use real temporary SQLite and the project's synthetic loopback Provider.

Both executions captured the same 16-file before/after source inventory (equal=true), original logs and exact private test source. The initial root implementation has four observed blocking gaps:

1. **A self-consistent replacement candidate is accepted without its real origin.** `AuthoringRepository.load` binds candidate to `view.summary.candidate`, but does not compare the stored Jobs terminal result to the current view/candidate. `AuthoringService._history` verifies the original Provider raw answer, but never proves that the candidate payload is the strict parse of that answer. The probe changes only candidate body/payload hash/body SHA, then owner summary candidate/record SHA; Provider artifact/receipt and Jobs result/event stay unchanged. `service.draft` returns successfully: the expected integrity rejection is an actual DID NOT RAISE. Fix needs both terminal/candidate/view association and original checked output-to-payload derivation; merely adding another self-consistent digest is insufficient.

2. **Undispatched revoked consent cannot be replaced by explicit consent for the same unfinished Job.** After real prepare/preview/grant, revoke occurs with zero transport requests. The worker sets Job failed; §20.8's same nonterminal Job re-preview path is unavailable. `read_prepared` only allows awaiting_approval with no active consent, while neither revoke handling nor worker restores that source stage. Preserve the old authorization/ACK history, return the source to an explicitly approvable state only after proving no dispatch instance began, and require a fresh explicit preview/grant. Do not replay a begun/unknown dispatch or have GET repair the state. The probe reaches actual failed vs expected awaiting_approval before its new preview.

3. **Mutable execution actor can borrow an unrelated currently privileged author.** The probe creates/grants as A, creates another real author session B, lowers A to learner, then changes only `execution_actor_id` plus owner record SHA to B. Original grant actor/consent history are untouched. Worker sends one actual loopback request, although B never granted this operation. `AuthoringRepository.load` currently checks only actor-null versus consent-null, and Worker reloads whichever actor that mutable field names. Bind execution actor to the actual original Provider grant command/authorization history, not to a well-shaped current owner field. This is a deliberate corruption fixture, not an HTTP write exploit claim.

4. **A valid control-only terminal cannot be read after authority returns.** A real Provider terminal is fully persisted; the probe then lowers author role before calling Authoring's finalization phase. The worker correctly uses Provider's control-only receipt, saves failed status without academic output, and the learner control read works. After restoring author role, `service.read` rejects with integrity error because the stored null answer/refusal is compared unconditionally with the original existing Provider artifact. Distinguish a deliberate, authenticated control-only adoption from a corrupt/missing previously adopted body. On restored permission, use the checked Provider owner read to project the original output without creating a candidate, rewriting history, or dispatching again. The probe deliberately controls the internal before-finalization seam; it does not claim a naturally timed browser reproduction.
