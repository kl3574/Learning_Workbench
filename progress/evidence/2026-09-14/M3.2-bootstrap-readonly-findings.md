## 有具体源码路径支持、尚未运行证实的候选因果

1. 初始 GET 取回上一用例的旧 Reader 和滚动位置，saved 标签先出现。
2. helper 旁路 reset 把服务端 revision 推进，同时旧 React 树仍在。旧内容的懒加载/策略核验后重新挂载/浏览器滚动事件可能继续触发 set。
3. 如果该 set 在 localStorage.clear 之后、reload 真正卸载前发生，它会按旧 live/base/ETag 重新写入本页 pending。
4. reload 复用同 client ID，读取真实 reset 后的新 revision 与该旧 pending，就会显示合法 CAS conflict，saved 等待自然超时。

这条时序解释了为什么“旁路 reset 成功”并不证明新页没有本机候选，但首次 CI 未记录它是否实际发生。不能据源码候选或后续重跑通过就宣称已找到/修复该次失败的根因。

另一个候选是首次重载 GET 短暂失败（queries.retry=false，hook 保留 offline 供显式重试）或请求超过断言窗口；日志同样没有 HTTP 状态/耗时来支持或排除，不据此增加 timeout 或重试。
