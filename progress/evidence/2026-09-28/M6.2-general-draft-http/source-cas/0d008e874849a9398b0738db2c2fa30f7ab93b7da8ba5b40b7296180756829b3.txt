# 0032: Exact historical text-block Draft editing

PRODUCT_DESIGN.md §§6.5, 7, 20.1–20.3, 20.8 and Appendix A 1262–1265 define the contract. This service slice implements a nonnull exact public text-block base, create and atomic title/body_markdown PATCH. Other kinds, null bases, nontext blocks and concept/dependency/private-body scope are explicitly unsupported. Strict application DTOs retain the full create-kind enum and recursive JSON patch values; this change does not register HTTP routes or expand Import GET.

The `authoring_edit` candidate owner is distinct from Import, single generation and group generation. Three owned tables retain the current editable head, immutable complete versions and permanent actor/workspace/route/key commands. A version binds its complete typed payload, physical UTF-8/LF body hash, exact historical base metadata and frozen provenance descriptor. Candidate revision is an edit CAS, not a publication lifecycle revision. No future ContentRef or approval is fabricated. Body/title changes produce exactly r+1, retaining the base and parent record hash; a complete no-op is rejected. Restoring old text here remains an unreviewed Draft; publishing old text as a higher Content revision needs a later explicit publishing slice.

Content and Provenance ports read on the caller's actual transaction. The exact public body is read and hashed; inherited citations, rights and warnings come from the frozen descriptor. This does not download or verify the private original's physical bytes, prove source truth, or transfer source approval. Missing provenance retains original citation IDs and an unresolved warning. A later Content current pointer does not substitute new text for the selected historical base. Every read, replay, write and Review material read revalidates the current session/author and current Authoring access Policy. This slice uses the existing protected authoring-material gate, including its open-book/protected-attempt restrictions; it does not define all future manual-edit access capabilities.

Create requires a key. PATCH requires expected_revision and optionally accepts a key; without one a stale retry returns 412. With a key, the original complete command and ACK survive restart, later edits and the generic 24-hour cache. Current access, exact base, entire immutable edit history and registered candidate history are checked before returning that original ACK. A new request with an occupied key and different body returns 409. SQLite writer serialization and a real head CAS prevent lost updates. Repository append uses a savepoint even when a wider transaction catches its error; service command/version/catalog writes roll back together. This owner does not stage new blobs or write Content/outbox records.

The forward migration preserves the existing 11-table FK closure under enabled foreign keys. It copies every ordinary column and rowid, rebuilds the original table names with only the two source-kind constraints extended, restores parent-before-child rows and all existing triggers, and checks bidirectional row equality before dropping temporary snapshots. Historic review and publication trigger transitions are not re-enacted. No old migration, core model or producer row is rewritten. The migration uses the existing online backup and transaction mechanism; actual nonempty Import/Review/publication history, synthetic persisted single/group shapes, full prior FK definitions and two rollback points are tested.

Quality receives an exact edit material union member. A new Review command requires the current editable head; an already queued worker, old Review read and original Review ACK remain bound to their original immutable candidate after later editing. A new revision receives no prior human decision. Machine structure reports only the schema and exact-byte checks actually performed; absent generated declarations and the absent numeric pipeline remain NOT_RUN. Mathematics, sources and independent pedagogy are never machine-approved. Existing current Policy, full Quality history, recursive evidence and physical report checks remain in force. Both admission and actual Import publication explicitly reject editing publication.

Resource limits are implementation budgets, not new content-quality rules: up to eight distinct patches; each JSON value up to depth 32, 10,000 nodes/container members and 2,000,000 string/key UTF-8 bytes; bodies up to 400,000 characters and 2,000,000 bytes; frozen provenance up to 2,000,000 bytes; complete owner history up to 1,000 versions and 32,000,000 stored JSON bytes. Invalid/nonfinite JSON, invalid Unicode scalars and CRLF body input are rejected rather than silently normalized. Errors and ordinary representations omit academic payloads; protected DTOs are fully reconstructed with serialization warnings treated as errors.

Tests use real local SQLite, Import/Review workers, Content/Provenance ports, current assessment Policy, competing connections, immutable storage constraints and injected failures. Persisted generated-owner migration shapes and explicit human decisions are labeled synthetic; no Provider, numeric executor or real human approval is claimed. HTTP/CSRF/header/generated-route integration, editor UI, general Draft GET/state projection, editing publication, dependency impact and overall M6.2 acceptance remain outside this slice.
