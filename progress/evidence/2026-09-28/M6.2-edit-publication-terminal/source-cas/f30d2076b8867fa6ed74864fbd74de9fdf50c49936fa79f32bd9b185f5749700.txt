# 0034: Explicit publication of an exact edited text block

PRODUCT_DESIGN.md §§7,9.3,15.1–15.3,20.1–20.3 and Appendix A define immutable Content revisions, four-field Draft publishing, exact human approval and atomic invalidation. This slice extends the existing POST `/drafts/{id}/publish` to the already implemented text-block edit owner. It does not add an editing GET, change the request/response DTO, substitute a ContentRef for a DraftCandidate or rewrite Import publication records.

A new command requires the current immutable edit head, the selected Review's complete current history and artifacts, structural PASS, all applicable human mathematics/source decisions and explicit real-warning acknowledgements. An edit has no declared numeric plan: absence is not a numeric PASS. Review continues to reject mathematical N/A for formulas in the current title/body. The inherited base is a real source and requires source approval. Decisions in automated tests remain synthetic protocol fixtures.

The Content owner separately compares the exact frozen base against its active current pointer under the same writer transaction. A mismatched/archived base yields412; no implicit rebase or last-writer-wins update occurs. Publication uses the same Content ID at base.revision+1 and changes only the reviewed title/body fields. Candidate SHA covers the edit payload; result SHA covers actual published ContentBlock metadata. These hashes serve different roles and are never conflated. Current pointer, immutable revision/body references, dependency outbox, existing retrieval/recommendation invalidation and exact note stale revisions share the publication transaction. This is durable impact intent, not completed impact analysis/reindexing.

A new internal edit-publication-v1 record binds the entire immutable edit record hash, exact base material, reviewed payload, admission observation, selected human receipt hash, actual result and permanent actor/workspace/route/key command. Existing Import draft-publication-v1 bytes and semantics remain unchanged. The publication lifecycle records current adoption/selection/verification and actual publication; it does not manufacture past approval times or mutate producer snapshots. Forward migration0020 preserves all four publication tables, rowids, FKs and immutable triggers, extending only the owner constraint to the existing authoring owner. It executes with FKs enabled and verifies copies bidirectionally before discarding temporary snapshots.

Original-key replay first authenticates current identity/Policy and the complete current owner/Review history, then verifies the original admitted decision and exact historical Content bytes. It returns the original ContentRef after later Content advancement or Review rejection. Previously committed PATCH commands likewise replay their original ACK before terminal-state checks; new PATCH commands cannot restart this published Draft. It does not use current-head/base CAS to erase a prior committed result. New keys still require current admission; different actors cannot inherit the old actor's command. Corrupt original edit/base/history/report/published bytes fail closed without repair writes.

The new revision deliberately has no invented Import provenance row. Its base provenance remains fully retained in the immutable Edit and publication records; the existing Reader returns original_source=null, unresolved citation IDs and PROVENANCE_UNRESOLVED for the edited revision. Explicit Draft sources approval is not relabelled as original Import parser attribution or a public Content review_state. Old Import provenance/membership and its commit/recovery rules remain intact. A future truthful derived-provenance projection needs an independent ownership design; this slice does not claim it exists.

A committed publication is terminal for new PATCH commands on the same Draft. The Edit owner consults the authenticated publication owner record under the same writer transaction after original-command replay. Concurrent PATCH/publication has only two serial outcomes: PATCH wins and the old reviewed publication candidate is rejected; or publication wins and the new PATCH is rejected without a new Draft revision. Creating a new Draft from an explicitly chosen current ContentRef remains the available safe operation. Editing UI/conflict recovery, derived Reader attribution, global Draft/Content review-state projection, generated/question/group publication, completed impact analysis and full M6.2 acceptance are not completed here. No Provider or numeric executor is required or invoked by this slice.
