The repeated CI failure was **not reproduced locally**. One original-test execution passed (9.8s reported), and one separate passive-instrumentation execution passed (10.6s reported). Both used the original 5000ms assertion, zero retries and isolated dynamic loopback services. No code fix or CI success is claimed. An earlier anchored selector found no tests; its exit-1 receipt is preserved separately as NOT_RUN, not a product failure or a passing attempt.

The detached checkout is 9eb9795a1da6b1a2ddc04605e710cd5d744e9396. All 949 non-progress tracked files were stable during each actual test. The original run matched this baseline. The instrumentation run differs in exactly four tracked files, with the complete patch and original/modified bytes retained: test factory, diagnostic observer, generated SSE decoder, and useTutor consumer. Two additional private helper/config files are retained. The original `tutor.spec.ts` is byte-identical to Git. No further runs were made to seek a green result. The active root numeric Python suite started at 08:12 UTC and ran concurrently on this same machine during both browser executions; ports, databases and profiles were isolated, but CPU, memory and scheduling were shared. These timings are observations, not an isolated performance benchmark or a model of GitHub runner capacity.

The existing heading cannot distinguish worker progress from stream progress. `tutorState.observeEvent` updates answer, usage and seq but deliberately leaves run.status unchanged. A terminal event triggers a fresh GET; only that accepted snapshot establishes completed. Thus a last-delivered queued heading neither proves the worker was still queued nor proves delta/usage frames were unconsumed. Likewise the old safeRun `provider_receipt_present` field tests **TutorRunView.result.provider**, not the Provider-owned ledger. Its absence cannot prove that Provider had not already committed its terminal receipt.

In the single instrumented local run, server spans measured approximately 1011ms from dispatch-start return to Provider receipt return, then 408ms to Tutor finish return. On the separate Node observation clock, the completed frame's decoded-stage notification arrived about 2163ms after assertion start; observed-stage notification followed about 0.6ms later, accepted completed GET about 116.5ms later, and delivered completed DOM about 2.6ms later. These are same-clock observation differences, not cross-clock server/browser latency. Notifications report code stages by an asynchronous binding, so they are not exact browser instruction timestamps. All original assertions passed. No consumed-frame evidence from this local run is projected backward onto the earlier failing CI runs.

The 2603 safe API events had no omissions. The maximum transaction-entry wait was about 332ms; a Provider guard call took up to 198ms; a Tutor read took up to 133ms. These are observations in a passing run. Many stages overlap; their summed durations are not elapsed wall time or proof of a unique slow path. Four Provider recovery operations encountered sqlite operational errors; the probe only records error class, so it does not prove those four errors were specifically SQLITE_BUSY.

Falsify this specific mechanism when no terminal was actually consumed before the boundary, or when accepted completed state and completed DOM were delivered within it. Queued heading and requestfinished alone are insufficient. |

Neither failing run recorded actual decoded frames. The local trace demonstrates that these measurement seams can distinguish stages, not which stage caused the CI failures.
