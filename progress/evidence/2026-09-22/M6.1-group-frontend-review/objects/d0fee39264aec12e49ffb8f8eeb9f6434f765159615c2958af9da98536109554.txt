## Spec

The original P1 is resolved within the reviewed scope:

- `DraftStore.save` checks the signal/predicate before and after opening storage, at the readwrite GET success callback, immediately before either normal or conflict PUT, and in the final PUT success callback. Both PUT branches use the same guard. Revocation before admission attempts a real abort and settles failure from the actual terminal event. `ACCESS_CHANGED` remains distinct from a successful save or server rejection.
- Final PUT success executes the last synchronous check immediately followed by `transaction.commit()`. This is the local authorization admission point. A successful commit request is not yet persistence success: only `oncomplete` resolves the saved/conflict result; a genuine abort still rejects. After admission the abort listener is removed, and later permission loss does not claim to roll back a committing transaction. Listener cleanup also occurs on abort and complete.
- `persistAuthoringCommand` validates access at entry, every retry and after each awaited load, before its synchronous existing-ACK/unchanged-record returns. Its saves receive the same guard. A completed admitted ACK is not erased merely because access changes afterward; the hook stops exposing or using it. CAS-conflict retry re-enters the guard rather than continuing under captured permission.
- `useAuthoring` creates one guard per academic operation and passes it through initial-command, ACK and non-Policy rejection persistence. The predicate checks current owner/workspace, session generation and operation identity. Subject clearing, scope cleanup and immediate session-access notifications abort the signal. A Policy rejection invalidates academic access before any error-journal write. Finally unsubscribes the session listener and releases the controller. Safe cancellation uses no academic guard and retains its original ACK behavior.

This distinction between admission and persistence matches the IndexedDB method algorithms: API `abort()` rejects a committing/finished transaction, while `commit()` starts committing from active state; the later complete event follows successful storage. [W3C IndexedDB 3.0 transaction methods](https://www.w3.org/TR/IndexedDB-3/#dom-idbtransaction-abort), [commit algorithm](https://www.w3.org/TR/IndexedDB-3/#commit-transaction). This is local frontend authorization sequencing, not an atomic check against an unobserved remote Policy change.

The installed fake-indexeddb transaction implementation was inspected and captured: its `abort()` also rejects committing/finished state, and its `commit()` changes active to committing synchronously. The test's `nativeCommit` variable denotes the original fake-indexeddb method, not a Chromium run. The positive control invokes that real test-engine commit first and then changes Policy; it is not evidence that post-commit abort succeeds.
