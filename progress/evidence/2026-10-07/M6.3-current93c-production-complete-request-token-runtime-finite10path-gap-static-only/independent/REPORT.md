## Conclusion

No independently completable and qualified production input-proof/model-only executor slice is evidenced by this existing composition within the present restrictions. Production stays deliberately unavailable. Adding a Protocol, serializer or empty registration would not satisfy those missing requirements.

## Actual code gaps

1. main.py uses ProofRegistry() when codex_proofs is absent and passes codex_executor=None by default. provider_budget.ProofRegistry constructs an empty CodexProofRegistry and deliberately keeps ordinary text proofs separate. Default production preparation therefore has no runnable proof profile, preview cannot fabricate a proof, and start must reject unavailable proof/runtime. These are correct fail-closed gates, not a current unauthorized-outbound defect.

2. provider_codex_profile defines only the closed codex-synthetic-runtime-profile-v1, codex-synthetic-model-request-v1 and SyntheticCodexProof formats. Its registry accepts only SyntheticCodexProof, requires synthetic-* models and explicit loopback, and prepares canonical SyntheticCompleteRequest bytes. That is a real complete producer for the synthetic peer language; it is not the final serialized model request produced by the actual App Server with all hidden prompt/history/tools/configuration/protocol packaging. RunnableTurnInput.runtime is this same closed synthetic type. There is no concrete production final-request producer in the bound preparation path.

3. The exact token rule is len(complete synthetic body), and the upper bound is 8*ceil(len(body)/8). The closure explicitly defines one octet as one synthetic token and marks production_model_claim=False. It does not provide actual model tokenizer/format overhead/capacity/version/alias validity evidence. The normal InputProof callback/registry does not supply such evidence automatically, and the named Codex seam prevents substituting ordinary Responses text proof for the different App Server request. A turn/start JSON serializer, tokenizer of visible text, or CLI usage response cannot close this gap under sections 20.5 and 20.17.1.1.

4. The only bound concrete turn executor is SyntheticCodexExecutor using an in-memory callable and the synthetic gate/result DTO. Its own execution module says wall checks cannot forcibly interrupt a blocking callable or prove CPU/memory/process limits. CodexTurnWorker.available delegates to injected executor.available; that registration alone cannot authenticate actual sandbox qualification. A production model-only executor must additionally freeze and enforce the turn binary/deployment/protocol/configuration closure, allow only the exact approved model request/destination, prohibit retry/redirect/auxiliary requests before any outbound byte, enforce output limits and all approved wall/CPU/memory/FD/process/output/core constraints, and return checked real execution facts. None is implemented by the synthetic executor. max_tool_calls=0 does not remove these requirements.

5. LocalCodexBootstrapRuntime is a separately pinned zero-model control runtime. It permits only fixed initialize/initialized/thread-start bytes and uses an 8-second control profile, with no account/login/turn/tool method. Its ready mapping and historical resource description cannot qualify the distinct turn profile or prove final model bytes/counting/network enforcement. The turn worker also restricts live control/file authority to the exact synthetic executor until a checked real stop mapping exists; returning an execution DTO is not production qualification.

## Why the gap cannot be closed independently in this turn

Section 20.17.9 explicitly permits contract/SQLite/peer/UI implementation with zero production outbound when proof is absent and requires true App Server/model acceptance separately. Section 20.17.1.1 requires a reviewed reproducible proof of the actual complete request; 20.17.1.2 requires a distinct frozen and enforceable runtime; 20.17.9 item 9 forbids probing a real model to discover safe defaults. Existing code supplies neither actual production request provenance/counting evidence nor a qualified model-only runtime. Host/runtime probes, credentials and model requests are excluded from this review. No new synthetic port, arbitrary HTTP/model entry, reinterpretation of old profile or weaker budget is proposed.

A future concrete adapter/profile could be implemented under the already approved contract without inventing a product requirement, but it needs a fixed actual producer plus independently reviewable proof and qualified boundary evidence. Purely local source edits could stage parts of that implementation; they could not honestly establish availability or finish its full qualification from the current evidence. The finite conclusion does not assert that no implementation is theoretically possible or that no uninspected external artifact exists.
