# M5.1 file-fallback staging recovery — independent v3 repair evidence

This incremental package preserves the real staging-recovery failure and repair separately from the prior v2 Provider ledger evidence. Prior v2 manifest SHA256 is `d9846e6d3c3928246d0256ad20745f8cfef0bb67c04ca2545b7c6d3c10165b86`, at `progress/evidence/2026-09-15/M5.1-provider-ledger-development`. V1/v2 originals and public candidates were not overwritten.

The initial five tests really failed: a child process terminated with `os._exit(77)` before the hard link, leaving one staging name; `os._exit(78)` after linking but before unlink left nlink=2; concurrent cleanup, initialization and a second writer completed while the original writer was paused. The same five cases then passed. Additional real initialization crashes before/after key linking, unsafe filesystem entries and unrelated-name preservation were checked. Final owned results: 50 passed in 2.84 seconds, Ruff passed, and mypy passed for six production files. Each original run log is bound by its receipt; these are focused development checks, not fixed-commit full-platform acceptance.

The fallback uses an exclusive lock on the already validated private directory inode. All cooperating initialization, writes, reads and cleanup use it. Acquisition has a one-second monotonic bound; it does not wait indefinitely. Kernel process exit releases the lock. Recovery only considers the reserved exact staging namespace inside the current-user 0700 directory; candidates must be no-follow regular files, current owner, exact0600, bounded size and nlink1 or2. A two-link candidate must share its inode with exactly one valid immutable secret/key destination in the same store. The complete candidate set is validated before deleting staging names. Symlinks, unsafe types/permissions, oversized entries, unrelated external hardlinks and three-link cases are rejected without deleting other candidates. This is mutual exclusion among fallback clients, not a claim of protection from a hostile same-user process bypassing the API or of physical erasure.

All archived source bytes are exact. `source/red/` includes the four inputs matching the recorded RED hashes. The RED test file was not archived during its run: it was recovered later by reversing the recorded post-GREEN test additions in a separate cache copy and verified byte-for-byte against the prior SHA256. That provenance is explicit in `red-source-recovery.json`; it is not mislabeled a contemporaneous original archive. `source/final/` contains all twelve frozen03 owner files.

Original files remain private and unchanged. Only non-source evidence home prefixes, and actual runtime identity/opaque secret locator/staging names in logs, are explicitly normalized or redacted. Synthetic source literals and assertions remain intact. Each manifest entry records original/public hashes, byte counts and exact transformation counts. Receipt hashes still refer to original logs; manifest public hashes verify derivatives. No DB, secret file, fingerprint key, runtime backup, paid-provider request, browser or real system-store credential is included. The repair does not add a system credential backend. Generated README metadata is separately bound and the manifest excludes itself from the payload aggregate.
